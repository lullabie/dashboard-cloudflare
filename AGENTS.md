formal certification. Avoid flattery and flowery language. Explain material
edge cases and practical limits without unnecessary process text.

Read `PROJECT-STATUS.md` before project work, then `docs/CONTEXT.md` and the
current design/plan. Direct user instructions govern scope. Research, partner
reports, previous approvals for other stages and repository access do not
independently authorize implementation, resource creation or release.

context and notification to Muse and Jules. Design review must precede app work.

change, private-data migration, merge or Jules implementation is authorized
by this setup. Required additional service cost stays $0. No automatic paid
fallback or upgrade.

Keep all personal context, credentials and private payloads out of source,
queries, fixtures, relay packets and external reviews. Use invented records.

transfer it into this repository or the proposed host.

Use relevant installed skills, connectors and plugins. Read `docs/TOOLING.md`;
check availability and permissions before claiming a capability is missing.

evidence. Preserve upstream notices when reviewed source is later reused.

`docs/COLLABORATION.md`. Preserve remote changes. Use explicit file allowlists,
`codex/` branches and non-forced updates. Never publish the whole old local
workspace, delete prior evidence or force-push. Keep chat output brief unless
the user needs a decision, approval or blocker explanation.

Keep facts, proposals and untested claims separate. Name the commit, runtime,
binding isolation and actual result for each test. Historical Node/libSQL,
Muse or model checks do not pass Workers/D1. Follow `docs/ACCEPTANCE.md`.
Do not reopen settled broad appearance, source or calendar-day preferences.
